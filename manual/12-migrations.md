# Migrations

You change the database schema explicitly: write a numbered file under `db/migrate/`, apply it, and keep `db/schema.sql` as the schema dump the tests load. Nothing changes the database until you run a migration command.

## The demo app's baseline

`snails new --scaffold` starts the demo app with one migration: its own posts and comments tables, stamped with a UTC version. `new` prints the next step:

```text
20261111210824_baseline.sql
```

```sh
snails migrate load
```

```text
applying 20261111210824_baseline
1 applied
[snails] schema dump regenerated (3 statements)
[snails] database ready
```

A plain `snails new` project has no schema, so `snails migrate load` prints `nothing to load`. That's normal: a project with no models needs no database file until a feature needs one. Its first migration is the first table you create.

`load` is the explicit setup command. It creates the database when it is missing, loads `db/schema.sql` when one exists, replays pending migrations to record which files applied, then refreshes the schema dump. A SQLite app gets its `storage/` directory with the project, so this works before the first boot.

Nothing touches the database on its own. `bin/dev` never creates, loads, or applies anything. An uninitialized database or a pending migration stops the boot before the build. It prints `snails migrate load` for a fresh database or `snails migrate apply` once the applied-migration record exists.

## Change the schema

Add a numbered file for every change. The timestamp keeps files in apply order. The example alters the demo app's `posts` table. Use your own table name:

```sql
-- Slugs give posts a stable URL segment.
ALTER TABLE posts ADD COLUMN slug TEXT;
```

`snails migrate status` lists which files are applied and which are pending.
`snails migrate apply` runs the pending files in order and records them:

```text
applying 20261112090000_add_slug_to_posts
1 applied
```

`apply` runs pending migrations and stops there. It doesn't regenerate the schema dump. `snails migrate dump` does that. `load` does both for an initialized database too.

## Keep the schema dump in step

The tests load `db/schema.sql`, so regenerate it after every schema change:

```sh
snails migrate dump
```

```text
[snails] schema dump regenerated (3 statements)
```

The generated file starts with this header:

```sql
-- Generated by snails migrate dump from db/migrate/*.sql — do not edit.
-- Edit the migration files, then re-run snails migrate dump.
```

`snails migrate status` shows where you stand at any time:

```text
[snails] 2 applied, 0 pending
20261111210824_baseline          applied
20261112090000_add_slug_to_posts applied
```

`snails migrate verify` confirms the schema dump still matches a replay of the migrations. `snails migrate check` exits non-zero while the database is uninitialized or anything is pending — the command to run before a deploy. It prints the repair command for the current environment.

## When another system owns the schema

A project can declare `DB_OWNER="external"` in `pins.toml`. With it, `load`, `apply`, and `dump` refuse to write DDL because the schema belongs to another application, and `check` still reports the uninitialized or pending state. Apply changes in the owning system and let `check` confirm the app sees the expected version.

By default, the app owns its schema. `db/migrate/` and `db/schema.sql` are then the only writers, and the migration commands are the only path.

PostgreSQL migrations are real DDL runs, not a local file copy. `migrate dump` and `verify` replay the migrations into a throwaway schema on the target named by `PG_URL` or `--database`, so a dump never writes to the deployed database.
